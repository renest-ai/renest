# restore-grant · 恢复码契约

> 状态:**v2 信封 + v1 载荷**(2026-07-18 复议裁定 A 落地;此前 v1 直发预签名的形态废止)。
> 本文件是恢复码的唯一权威文本。实现:saas `app/routers/grants.py` + `app/schemas/grant.py`;
> 消费:oss `renest/restore.py`、`scripts/restore.sh`(逃生舱,curl+jq)、将来桌面/broker。
> **恢复码与授递码是两个对象**:恢复码=机器面凭据(本文);授递码=账号面转移凭证
> (控制台签发/兑换,不含下载能力,永不落到机器)——两者互不相认,严禁混用。

## 1. 三句话(用户可见口径,先于一切字段)

恢复码几天内有效,**绑第一台兑换它的机器**,随时可以撤销;过期、丢了、或者要换台机器用,
再签一份就是;包永远在你账号里,能登录就永远签得出码。

> 这个绑定是真的(2026-08-11 起),不是一句承诺:兑换时机器把自己几个稳定标识的哈希报上来,
> 先到先绑,换一个就拒。**同一台机器重复兑换是断点续传,照旧放行。**
> 首次兑换没报标识的码则永远不绑 —— 那时本来就没有东西可绑,拒绝只会把合法持码人挡在外面。

## 2. v2 信封(签发时得到的东西)

```json
{
  "grant_version": "2",
  "grant_id": "<ULID>",
  "nest_id": "<manifest.id,内容身份>",
  "issued_at": "<ISO8601>",
  "expires_at": "<ISO8601,签发时效=业务参数,默认 3 天,1h-30d>",
  "manifest_sha256": "<64hex>",
  "origin": "<SaaS 基址;兑换与进度上行同源>",
  "exchange_url": "<POST 此地址兑换 v1 载荷>"
}
```

- **信封不含任何预签名 URL**——码=服务端可兑换令牌,预签名降为兑换后的内部实现;
- 旧消费者(只认 v1)遇 v2 必须**显式拒绝**(MAJOR 语义,冻结契约既有规则);
- 码即凭证(ULID,不可猜);可吊销(吊销后兑换与进度上行立即 410);
  每次兑换服务端落审计(计数/时间/IP)。

## 3. 兑换(机器侧,无登录态)

`POST {exchange_url}` →

- `200`:**v1 冻结形状载荷**(见 §4),内含全新短命预签名(内部参数 ≤6h,
  且不超过码剩余时效);每次兑换都重跑供给校验(黑名单二次撞库——签发后下架的内容兑不出);
- `410 GRANT_REVOKED / GRANT_EXPIRED`:重签一份即可,包一直在账号里;
- `404 GRANT_NOT_FOUND`:未知码。

**断点续传** = 同一码重复兑换:journal 已校验的文件不重下,预签名中途过期就重兑。
一码一跑:进度上行以 grant_id 为 run 身份(broker_runs.id=grant_id,幂等)。

## 4. v1 载荷(兑换响应;冻结,extra=forbid,字段一字不多不少)

```json
{
  "grant_version": "1",
  "grant_id": "<同信封>",
  "nest_id": "<manifest.id>",
  "issued_at": "<本次兑换时刻>",
  "expires_at": "<本次预签名到期时刻>",
  "manifest_url": "<预签名 GET>",
  "manifest_sha256": "<64hex>",
  "blobmap": { "<sha256>": ["<主源url>", "<第二源url>", "…"] },
  "meta4": null,
  "handed_off_from": null,
  "handed_off_relayed": null,
  "retention_days_left": null
}
```

`handed_off_from`:这个包是**谁授递给你的**(发送人展示名);`null`/缺席 = 你自己打的包。
**服务端事实**——取自 `nests.claimed_from_user_id`(转存时写入),**绝不取自 manifest**:
被检查的东西不能自己提供检查规则,否则恶意包声明"我可信"就自解了。
恢复端据此对"别人给的包"用更严的姿态(依赖源异常时,除点名域名外还须点名发送人;
无差别放行对这类包一律无效)。本地 BYOS 自签的 v1 载荷不写这个字段 = 视同自己的包,行为不变。

`handed_off_relayed`:**给你包的这个人,自己是打包的还是转手的**(`true` = 他没打过这个包,
是从别人那儿收到后转给你)。只在 `handed_off_from` 存在时有意义;`null` = 不确定。
防的是**洗白**:恶意者把毒包给不知情的中间人,中间人转手后,收包人看到的是自己信任的名字,
却不知道对方根本没打过这个包 —— 名字是真的,信任是错付的。
**刻意只给这一个比特、不给上家身份**:授递是私密的,上家没同意被公开;
且发送方本来就看不到谁收了他的包,单向暴露上家会破坏这个对称性。
收包人拿到这一比特就够追问一句"你确认过这个包吗",这正是我们希望他问的。

`retention_days_left`:签发这份码的账号,**免费档保管期还剩几天**;`null`/缺席 =
这条规则跟他无关(付费档,或该功能未启用)。免费档的资产保管 90 天,**登录一次网站**
即重新起算;60 天起发召回邮件。这个字段存在的唯一理由是**堵住一种静默误杀**:
免费用户完全可能在 pod 上天天用恢复码复活、就是不开网页,而续期只认网站登录 ——
不在恢复现场说一句,他会在明明还在用的时候被清掉。故消费方在 `≤ 30` 时**必须**
把倒计时打给用户看。**只告知不阻断**:这个字段永不改变恢复行为(逃生舱纪律)。
本地 BYOS 自签的 v1 载荷不写这个字段 = 不显示,行为不变。

v1 载荷仍可作为独立文件消费(CLI 与逃生舱直接吃)——本地 BYOS 签发面继续产 v1,不受影响。

## 4.9 为什么"必须有人替逃生舱签" `[ B2,结构性理由]`

这一节不是背景介绍,是**恢复码这个东西为什么必须存在**的理由。写死在这里,
免得后人看到"又要签一遍链接"觉得多余、想把它优化掉。

**既有红线 给逃生舱定的依赖清单是 curl / jq / sha256sum(或 shasum)/ git / tar / uv。
里面没有 openssl,也不会有。** 而 SigV4 预签名需要 HMAC-SHA256 —— 上面那套工具**算不出来**。

所以结论是结构性的,不是实现偷懒:

> **私有桶的字节,逃生舱永远只能消费别处签好的链接,不可能自己签。**

于是"谁来签"就分成两条路,两条都产出**同一个 v1 载荷**(§4):

| 用户 | 谁签 | 怎么拿到 |
|---|---|---|
| 有 Renest 账号 | **服务端** | v2 信封 → 兑换(§3) |
| 不注册、用自己的桶 | **他自己那台有钥匙的机器** | `renest presign --nest <id> --out code.json` |

两条路的产物对消费方**完全等价**——这正是 §4 载荷冻结的价值所在:
逃生舱与代理层各只需要认识一种东西。

**推论(别绕过它)**:任何"让逃生舱直接拿桶密钥去取字节"的设计都是错的 ——
它既破既有红线(要新依赖),又把长期钥匙送上了执行端(破既有红线)。
要在执行端取私有桶的字节,**只有预签名这一条路**。

## 5. 消费方义务

| 消费方 | 义务 |
|---|---|
| `renest restore --grant <文件/URL>` | v2 → 自动兑换;v1 → 直接消费;过期预签名 → 重兑续传;上行 origin 取信封在册值;`retention_days_left ≤ 30` 时打倒计时 |
| `restore.sh`(逃生舱) | `GRANT=<文件/URL>`:v2 用 curl POST 兑换,jq 抽 manifest_url/blobmap;`retention_days_left ≤ 30` 时打倒计时;只依赖 curl/jq |
| broker/桌面(将来) | 同 CLI;吊销语义必须尊重(410 即停,不缓存旧预签名) |
