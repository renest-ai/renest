## 1. 顶层结构总览

一份 manifest = 一次**已验证成功运行**的完整自包含描述。核心字段**场景
中立**(候鸟原则:核心层永不出现任何特定工具的名词);场景专属信息进
`adapters.*` 命名空间。`[schema title]`

`additionalProperties: false` 全程生效 —— 顶层与每个对象都拒绝未声明的键。
**唯一的例外是 `adapters` 下的未知 adapter 键** —— 2.0 起它们被按不透明对象放行(§6.1)。

**但"未知字段"与"未知小版本号"是两件事,别混**(2.3 写死,见 §2「读者义务」):
schema 校验拒绝未声明的键(那是 `renest lint` 的职责),而**恢复端遇到同大版本的
更新小版本必须放行**,因为按规范那只会多出可选字段,拒收它等于把一个字节完全
能还原的包变成砖。

| 字段 | 必填 | 类型 | 一句话 |
|---|---|---|---|
| `format_version` | ✔ | 枚举 `2.0` … `2.8` | 格式版本号(唯一真相源是 schema 的枚举) |
| `id` | ✔ | string(ULID) | 包唯一标识,26 字符 Crockford base32 |
| `created_at` | ✔ | date-time | 落袋时刻 |
| `name` | | string ≤120 | 用户起的名字 |
| `base_image` | | object | 环境地基,digest 钉死。**2.3 由必填改可选**(§3) |
| `runtime` | ✔ | object | Python / CUDA / GPU 运行时参数 |
| `gpu` | | object | 打包这台机器的显卡事实(见 §3.2) |
| `fingerprint` | | object | 环境指纹 Layer 1(预检用) |
| `code_deps` | ✔ | array | 代码依赖(源码全量落袋),每条必须标 `role` |
| `python_lock` | ✔ | object | uv 确定性依赖锁(**2.3 起 `lockfile` 子字段可选**) |

`runtime`、`code_deps`、`python_lock`、`files`。其余可选。
(2.3 把 `base_image` 从这个名单里拿掉了 —— 理由见 §3。)

### 1.1 打包端的一条通则:拿不到就整块不写,永不写占位文字 `[实测]`

**2.3 起这是规范级要求,不是实现偏好。** 打包端问不出某一栏时,**把那一栏整个略去**,
不许写 `<fill in ...>` 这类"请在这里填"的占位语。

为什么写进规范:占位文字**过不了本格式自己的形状检查**(镜像指纹必须是 `sha256:`
加 64 位十六进制,占位语永远匹配不上)。2026-08-04 把历史上打的存档全验了一遍,
**一份合格的都没有** —— 病根就是这条纪律当时只是口头的。

分工也随之定死:**schema 允许缺席,`renest lint` 用告警说「信息不全」**
(`base-image-missing` / `lockfile-missing`),**占位文字则是 error**
(`placeholder-left-in`)。缺席是诚实的,占位文字是假装填了。
**不加任何 draft / completeness 标志字段** —— 那会造出第二个真相源。

## 2. 包标识与元数据

### `format_version` — 枚举 `2.0` / `2.1` / `2.2` / `2.3` / `2.4` / `2.5` / `2.6` / `2.7` / `2.8` `[schema]`

**唯一真相源是 schema 里那一栏的 `enum`**,别处(包括本文件)都是复述,
改版本只改那一处 + 代码 + 升版清单顶行 + 应急脚本的版本闸(四处有绊线测试盯着)。

**版本策略**:小版本升级 = 只新增可选字段或放宽约束;大版本 = 破坏性变更,旧读者必须拒绝。
2.0 是大版本 —— `code_deps[].role` 由无到**必填**。
**纯增量也要升小版本**:本项目先例是 2.0→2.1 只加了一个可选字段,照样升了号 ——
版本号要回答的是「你手上是哪一版」,不只是「能不能读」。
**与 `fingerprint.fingerprint_version` 独立演进**(§9-a)。

#### 读者义务(2.3 写死,是义务不是选择)

1. **同一个大版本之内,遇到不认识的可选字段 → 必须忽略,不得拒包。**
   严格校验是 `renest lint` 的职责,不是恢复端的义务。
2. **遇到比自己认识的更新的小版本号 → 告警放行,不得拒包。**
   落点:`renest.restore.newer_minor_within_major` 与应急脚本里的 `2.*` 分支。
3. **跨大版本仍然硬拒** —— 大版本号的含义就是「有破坏性变更」,猜就是瞎猜。

**为什么要把这条写成义务**:2.1 那一轮明明是纯增量,应急脚本的版本闸当时写死
`= "2.0"`,于是**一个字节完全能还原的包被拒成砖**,合并时才被测试抓住。
那不是谨慎,那是把用户的东西弄丢了一半。

**读者必须拒绝 1.x 包**,且要报「版本不支持」而不是崩在别处。这不是洁癖 ——
1.x 包没有 `role`,而猜 role 就是猜「这个包里哪部分是应用、哪部分是用户
自己的代码」,猜错就把用户的训练配置当成宿主展示给收件人看。

### `id` — ULID `[schema]` `[实测]`
`pattern ^[0-9A-HJKMNP-TV-Z]{26}$`:26 字符大写 Crockford base32(ULID 形态)。
T5 真实样本 `01KXFKYGAR47XHEK8G60PHNRFQ`。消费者:blob 寻址无关(blob 走
sha256),此 id 只标识"这一次落袋"。

### `created_at` — date-time `[schema]`;`name` — string ≤120 `[schema]`
`created_at` 落袋时刻(ISO 8601)。`name` 用户可见名字,可选。

## 3. 环境地基:`base_image` / `runtime` / `gpu` / `fingerprint`

### `base_image`(**2.3 起可选**)`[schema]` `[实测]`
环境的地基(容器镜像),用镜像仓库给它算的内容指纹(digest)钉死,
tag(`:2.4.0` 这种人给起的标签)仅作人类可读参考。

| 子字段 | 必填 | 说明 |
|---|---|---|
| `ref` | ✔(块内) | 如 `runpod/pytorch:2.4.0-py3.11-cuda12.4` |
| `digest` | ✔(块内) | `sha256:<64hex>`;按镜像名向仓库反查得到 |
| `digest_kind` | | **2.3 新增**:上面那个指纹是哪一层的,枚举 `platform` / `index`(见下) |

**为什么 2.3 把它降为可选** —— 一个持续两年的三方矛盾:
schema 把它列为**必填且格式严格**;而打包时**容器拿不到自己的镜像名**
(2026-07-13 真机实测的边界);而重建**根本不需要它**(实测:带占位语的存档照样还原成功)。
于是唯一的活路是写占位文字,**而占位文字过不了这份 schema 自己的格式检查** ——
2026-08-04 全量核验历史存档,一份合格的都没有。**该改的是必填这一侧。**

**块内两栏仍然必填,格式一个字不松。** 放宽的是"这个块可以整个不出现",
不是"出现了可以只写一半":半份地基比没有地基更误导 ——
下游会照着一个查不到的镜像名去拉。查不到指纹就整块不写(§1.1)。

**存续性,两句必须说的诚实话** `[实测]`:

1. **镜像本身不落袋。** 包里存的是「我们当年跑在哪个镜像上」这条记录,不是镜像的字节。
   所以重建的系统层(操作系统、驱动、CUDA 运行库)**依赖镜像方仍然活着**;
   镜像被删或被覆盖,这一栏就只剩考古价值。
   这与 `python_lock.pinned_wheel_urls` 那条披露同一性质:
   **能落袋的落袋,落不了的如实说,不假装覆盖。**
2. **多架构镜像记的是"平台指纹"而不是"索引指纹"。** 同一个 tag 在 x86 与 ARM 上是
   两份不同的镜像,上面还有一层索引把它们串起来,各有各的指纹,而两者**长得一模一样**
   (都是 `sha256:` 加 64 位十六进制),光看值分不出来。所以:**拿到哪层如实标哪层**
   (`digest_kind`:`platform` = 某一个 CPU 架构那份,**这是我们想要的那个**;
   `index` = 串起多个架构的那层),**标不出来就不写这一栏,不换算、不猜** ——
   记错一层,照它拉镜像会拉到另一个架构的东西,而那种失败的报错指不到真因。

裸机 / 无容器场景见 §9-e(2.3 起这个格子有答案了:整块不写)。

### `runtime`(必填)`[schema]`
| 子字段 | 必填 | 说明 |
|---|---|---|
| `python_version` | ✔ | `^3\.\d+\.\d+$`,如 `3.11.9` |
| `cuda_version` | | 如 `12.4` |
| `gpu_model` | | 创建时 GPU(如 RTX 4090);**参考信息,非重建约束** |
| `driver_version` | | 驱动版本 |
| `libc_version` / `platform_tag` | | **2.4 新增**:决定一个预编译轮子(wheel)在这台机器上装不装得上的两项 |
| `native_libs` | | **2.6 新增**:跑通那一次要机器自己提供的操作系统库有哪些 |
| `contested_modules` | | **2.8 新增**:几个已装的包往同一个目录写文件时,跑通那一次用的那份属于哪个包 |

`gpu_model` 明文标注为"非重建约束" —— 换卡重建合法。

**`libc_version` / `platform_tag`(2.4 新增)** —— 前者是这台机器的 C 运行库版本
(如 `2.35`),后者是这台机器上 Python 报出来的平台标签(如 `linux-aarch64`)。
预编译轮子是照着它们挑的,所以在较新的 C 运行库上打的包,可能带着一批老机器装不上的轮子。
**权威是平台标签,不是 C 运行库版本一项** —— 实测一台机器能接受 690 个标签,
C 运行库只是塑造这份清单的因素之一。**两项都只作提醒,永不用来拒绝重建。**

**`native_libs`(2.6 新增)** —— `{ "method": "loaded" | "declared", "names": [...] }`。
这些库属于机器上那套操作系统发行版,不属于存档,所以**打不进包里**;
缺一个的机器逐字节还原全对、应用也起得来,却会**整个插件静默失效** `[实测]`。
三条义务,每一条都是量出来跟直觉相反的:

| 规矩 | 为什么 |
|---|---|
| 名字**按程序索要时的原样抄**,两个方向都不许规范化 | 多数条目指的文件在磁盘上根本不叫这个名 —— 索要的是 `libcuda.so.1`,磁盘上那个文件名里带着驱动版本;还有一个包索要的名字里本来就带小版本号 `[实测]` |
| **"机器提供的"由打包那一刻它实际从哪儿加载来判定**,永不按名字去查 | 有个常见压缩库,同名文件在某个已装的包里也有一份,而运行时加载的是机器那份;按名字查在两种芯片上都判错了 `[实测]` |
| `method: "loaded"` 可以用来拦重建;**`method: "declared"` 永远只许告警** | `declared` 是"找不到正在跑的那个应用"时的兜底,它只覆盖真实加载量的一部分,同时又列出一堆压根没被加载的库 —— 有台机器缺了其中四个,照样正常出图 `[实测]` |

**`contested_modules`(2.8 新增)** —— 数组;每一项描述一个"锁里几个包都往里写文件"的顶层模块:

```jsonc
{
  "module": "cv2",                        // import 名 = 它们共同写的那个目录名
  "candidates": ["opencv-python", "opencv-contrib-python", "opencv-python-headless"],
                                          // 锁里会装的、都写这个目录的包,按锁里顺序(至少 2 个)
  "winner": "opencv-python-headless",     // 跑通那一次用的那份属于哪个包;必须是 candidates 之一
  "winner_evidence": {
    "file": "cv2/cv2.abi3.so",            // 相对 site-packages:决定行为的那个编译文件
    "sha256": "9e29…(64 位十六进制)",     // 该文件**装完之后**在打包机上的指纹
    "method": "record_hash"               // 靠什么认出赢家:record_hash | libs_dir
  }
}
```

**格式为什么要带它 `[实测]`。** OpenCV 一家三个包都解进同一个 `cv2/` 目录,谁最后装谁就是
运行时用的那份 —— 而这份决定这个模块要机器提供哪些操作系统库(带界面的两个变体向机器要
`libGL.so.1` 与 `libxcb.so.1`,无界面那个不要)。锁钉住的是名字和版本,**不是安装顺序**,
而安装器是并行的:同一份存档在同一台机器上背靠背还原三次,三次里有一次装出的赢家不同,
`pip list` 三次逐行相同。所以锁和包清单都答不了"运行时是哪份",只有打包机知道跑通那次
用的是哪份,也只有装完的文件字节能认出它。打包机上认赢家有两条路,按这个顺序试:
`record_hash` —— 某个候选包自己的安装记录里登记着这个文件、且哈希与磁盘上一字不差;
`libs_dir` —— 赢家自己的库搜索路径指向某个候选包随包带的库目录(`opencv_python.libs` 之类)。
两条都认不出 → 打包端**整段不写**,并在报告里说一句。

**指纹取的是打包那台机器上装完之后的文件,永远不是轮子里那份;它也不是对别的机器的承诺 `[实测]`。**
同一个包的同一个版本会发好几种构建 —— 每种芯片架构一种,OpenCV 一家在同一架构上还发两种 Linux 构建 ——
装到哪一种取决于装它的那台机器。所以同一个包在 ARM 机器和 x86 机器上量出来是两个指纹;换了芯片的机器
(或安装器挑了另一种 Linux 构建的机器)把赢家重装之后**仍可能**指纹不同。这种结果叫"同一个包、不同构建":
说出来,不拒绝。(安装器**不会**改写文件:在一套用 uv 装出来的环境上量过,赢家文件的字节与它自己那个包的
安装记录一字不差 —— 这正是 `record_hash` 排第一位的依据。)

**消费者义务(两条还原路径,以及你自己写的任何读取器)。** 装完依赖后,对 site-packages 下的
`winner_evidence.file` 算哈希。与 `sha256` 相同 → 什么都不做。不同 → **只把 `winner` 那一个包**
按锁里给它的版本、不带依赖地重装一次,让它最后写盘;再算一次。这次相同 → 说一句"重装了它"。
仍不同 → 说出来,继续(换了芯片架构、或安装器挑了同版本的另一种 Linux 构建,字节本来就不同;
不管哪种,赢家现在都是最后写盘的那个)。**永远不许因为这个字段拒绝存档**:它是 declared 级陈述,只许告警
(与 `native_libs.method: "declared"` 同一条线)。没有这个字段的存档,行为与从前完全一样。

**写入方规矩。** `winner` 必须是 `candidates` 之一;每个候选必须是锁里会装的包;`candidates`
至少两项(一个包构不成争夺);认不出赢家就**不写**,不许猜。`renest lint` 拒绝
"赢家不在候选里",在能读到锁的时候也拒绝"候选不在锁里"。

### 3.2 `gpu`(可选)—— 打包这台机器的显卡是什么样 `[schema]` `[实测]`

显卡区块。"文件逐字节全对、内核却加载不起来"这一类失败,就是靠它跟别的分开的。
打包机上没有显卡工具链时**整块不写**;代理层拿它做**阻断级**预检,逃生舱只告知。

| 子字段 | 起于 | 说明 |
|---|---|---|
| `captured_on` | 2.0 | 打包时那张卡:`name`、`sm_arch`(形如 `sm_86`)、`cuda_compute`(如 `8.6`) |
| `torch_cuda_arch_list` | 2.0 | 这个环境里的 PyTorch 到底带了哪些代际的编译产物 |
| `node_native_archs` / `package_native_archs` | 2.0 | 逐个二进制的编译档:前者是扩展自带的,后者是 pip 装进来的(见 §3.1) |
| `min_vram_gb` | 2.0 | 只表达性能预期。**今天没有任何代码写它**,留着是为了已经带着它的老包 |
| `observed_use` | **2.4** | 跑通那一次**被看到**用了多少显存:`max_used_bytes` / `sample_interval_s` / `samples`,三项必须同时出现 |
| `shares_system_memory` | **2.4** | true = 这台机器没有独立显存,跟系统内存共用一份 |
| `device_count` | **2.4** | 机器上有几张卡。不填 = 不知道,按一张处理 |
| `peer_access` | **2.4** | 多卡时,两张卡能不能直接读到对方的显存 |
| `peer_link` | **2.5** | 多卡时,**它们之间靠什么通**,枚举 `nvlink` / `pcie` |
| `total_bytes_rounded_gib` | **2.4** | 每张卡的显存总量,**故意只留整数 GiB** |

**`observed_use`(2.4)—— 这是"看到的最大值",不是真正的峰值。**
应用自己不记这个数,采样的是另一个进程,它能做的只有每隔几秒问一次"还剩多少",
把见过的最大用量留下来。间隔那么长,一个短暂的尖峰完全可能漏掉,所以**真实峰值只会更高,
不会更低**。**因此这个数字永远不许单独出门** `[实测]`:一次跑报的是 68 个读数里的
3523 MiB(有意义),另一次报的是 5 个读数里的 1 MiB —— 因为它还没碰到显卡就崩了;
只拿到"1 MiB"的人会得出"这活几乎不吃显存"的结论。
**目标机器显存不够这个数时只许告警,不许把机器拦下来** —— 它天生就是一个偏低的地板。
**不填 = 没量,不等于"不吃显存"**:显存与系统内存共用的机器上,常规查询压根问不出东西,
所以那里缺席是常态,不是错误。

**`shares_system_memory`(2.4)** —— 这类机器报出来的"总量"是整台机器的内存
(实测有一台是 121.7 GiB),而按卡查询什么也问不到;在那儿量出来的显存数字,
与有独立显卡的机器**不可比**。读数两边都说不清时就不写:一个错的标记比一个空的更坏。

**`peer_access`(2.4)与 `peer_link`(2.5)—— 两个问题,谁也推不出谁** `[实测]`。
只看卡数会误导:一台装了两张 24 GB 卡的机器,两个方向都报"到不了对方",
那这两张卡就不是一个 48 GB 的池子,把模型切开分到两张卡上的配方在那儿必失败,
而卡数看上去完全正常。而且它**只能量,不能推**:两台机器的卡都只是挂在主机总线上、
都没装桥接件,答案却**相反**。2.5 的由头是:光记"能不能到"把真正要紧的差别藏起来了 ——
同一晚量的四台机器里,有两对卡都答"能到",一对走的是专线(每张卡 12 条,每条 25 GB/s),
另一对只是共用主机总线。对人们真正要问的那个问题(这两张卡能不能当一张大卡使),
这两者根本不是同一个答案。`peer_link` 取自驱动工具的拓扑图(两张卡之间标着 `NV4` 之类 =
专线;`PHB` / `NODE` / `SYS` = 主机总线或更远),**不填不等于 `pcie`**。

**`total_bytes_rounded_gib`(2.4)—— 故意取整** `[实测]`:两台装着同型号卡的机器,
报出来的总量差了约 7 MB,因为各家主机预留的量不一样。逐字节比,两张一模一样的卡看着不一样。
先取整,再比较。

### `fingerprint`(可选)`[schema]`
环境指纹 Layer 1:restore **前**的成功率预检用,**只收场景中立的功能性
复现字段**。职责 = "能不能装成"的前置判断,与"装什么"的配方字段(`code_deps`
/ `python_lock`)**不重叠**。采集时点 = "打包完成、应用能正常启动后"那一次。

| 子字段 | 必填 | 说明 |
|---|---|---|
| `fingerprint_version` | ✔ | const `"1"`;与 `format_version` 独立演进 |
| `python.version` | ✔ | 如 `3.11.9` |
| `torch.version` / `torch.cuda_version` | | 节点冲突头号元凶(实测最常见的一类冲突) |
| `os.name` / `os.version` | | 操作系统 |
| `os.machine` | | **2.3 新增**:打包这台机器的 CPU 架构(见下) |
| `critical_packages` | | 键=包名 值=版本(如 xformers / insightface) |

**`os.machine`(2.3 新增)** —— 取 Python 的 `platform.machine()` 输出,
值形如 `x86_64`(绝大多数云主机)或 `aarch64`(ARM 架构)。

**为什么加**:主流云已经有 ARM 架构的 GPU 机型在卖。跨架构重建时,
锁文件里钉死的安装包直链、以及记下来的容器镜像**在另一种芯片上全部作废**,
而失败时报出来的错**指不到真因** —— 用户看到的是某个包装不上或者动态库加载不了,
想不到是「这台机器的芯片跟当年那台不是一回事」。

**跨芯片家族是必然失败,不是风险** —— 这句由 2026-08-08 真机采样定性
():Python 的依赖包是
**分芯片编译的,一个芯片一份**,Intel 机器上打的存档搬到 ARM 机器上**压根装不上**。
所以消费侧对这一栏的正确力度是**硬拦**,不是"提醒一句、你可以继续"。

**本版只负责如实记下来(格式的事);硬拦归预检那一侧(实现的事,欠着)。**
记录本身不参与成败裁决;当前**两个方向都还没有人拦**,欠账记在 内部欠账清单。
探不到就不写这一栏(§1.1)。

**边界**:此区块**不记 ComfyUI core commit**(它已由
`code_deps[].commit` 钉死,记两遍即两个真相源);**禁止**出现主体画像键名
(如 `ss_tag_frequency`)。消费纪律:`restore.sh` 对指纹**只告知不阻断**;
分级阻断在代理层(/ restore-protocol §2)。`runtime` 与 `fingerprint`
的字段重叠见 §9-c。

## 4. 配方:`code_deps` / `python_lock`

### `code_deps`(必填,数组)`[schema]`
代码依赖(应用本体、装进它的扩展、用户自己的脚本与配置)。**源码归档
全量落袋,不依赖上游存活**。每条:

| 子字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✔ | 依赖名 |
| `role` | ✔ | **2.0 新增必填**,枚举 `host` / `extension` / `user_code` |
| `repo_url` | | uri。**2.0 由必填改可选** |
| `commit` | | `^[a-f0-9]{40}$` 完整 40 位。**2.0 由必填改可选** |
| `archive` | ✔ | 源码 tar.gz 的 blob(见 §7) |
| `install_path` | ✔ | 相对环境根的落位路径 |
| `post_install` | | 该依赖专属安装后命令(逃生舱,尽量少用) |
| `upstream_match` | | **2.2 新增**:这份代码跟它声称的上游一不一致(见下) |
| `license` | | **2.2 新增**:这份代码的许可(结构见 §8) |
| `exclude` | | **2.6 新增**:字符串数组 —— 打包时故意没放进这份归档的东西 |

#### `code_deps[].exclude`(2.6)—— 让人分得清"完整源码"和"被裁过的源码"

这一栏打包输入清单里一直有,清单里却被扔掉。于是收件人(包括半年后的你自己)
**分不出包里这份代码是完整的还是被裁过的**:同一个仓库、同一个提交号、少了一个目录,
而清单上看不出任何异样。它同时记两件事:输入清单要求排除的,以及**打包端自己决定丢掉的**
(它认为该重编译的 `.so`、`build/` 目录),因为收件人问的是"这份归档缺了什么",
不是"是谁决定缺的"。

**这是披露,不是指令。** 读取端把归档原样解开就行,这里没有任何东西需要被重放。
每一条的含义与打包输入清单里一致:**锚在归档根上** —— 写 `models` 只删顶层的 `models/`。
这个锚点不是细节:曾经有一版按裸名字逐层匹配,把源码目录一起剥掉了,
存档按哈希校验全绿,一启动就死 `[实测]`。常规垃圾(`.git`、`__pycache__`)自动清掉,不列。

#### `code_deps[].upstream_match`(2.2)—— 拦住"拿一个流行扩展、加三行私货"

| 子字段 | 必填 | 说明 |
|---|---|---|
| `state` | ✔ | 枚举 `clean`(与上游一致)/ `modified`(被改过)/ `no_upstream`(不在任何 git 仓里) |
| `changed_files` | | integer ≥0;`state=modified` 时有几处未提交的改动 |

**这是唯一能拦住"拿一个流行扩展、加三行私货"的一行披露** —— 而那正是投毒最典型的手法。
**逻辑早就有了,只是结果被扔掉**:算这件事的代码一直在跑,结果只进了给打包人看的提示、
不进清单,于是**收件人永远看不到**。

`no_upstream` 是**诚实的一档,不是失败**:微调用户的配置与启动脚本本来就不在任何 git 仓里。
**拿不到上游身份时整块省略,不猜** —— 有一个专门处理过的坑:目录自己没有版本库信息时
会向上找到外层仓库,把宿主的身份错安到扩展头上,**错坐标比没坐标更危险**。

`renest lint` 另有三条语义闸(schema 只管形状):说"被改过"却不说改了几处 → 告警;
说 `clean`/`no_upstream` 却又报了改动数 → 报错;说"不在任何仓里"却又给了仓库地址 → 报错。

#### `code_deps[].license`(2.2)—— 补一个结构性空白

**在此之前:模型有许可字段,代码一个都没有。** 而宿主应用是那种"用了我你也得开源"的
传染性协议,扩展五花八门,里面有禁止商用的、也有更严格的。**授递一个包 = 再分发这些源码。**

传染性协议那一侧我们**碰巧是合规的**(源码全量随包走,正好满足"附源码"的要求)——
**但那是运气不是设计**;非商用扩展被转给一个商用用户,在 2.2 之前没有任何字段能拦、能提示。
结构与 `files[].license` 完全相同,见 §8。

**`role` 为什么必填,而且用这三个中立词**:
- `host` = 被跑起来的那个应用本体;`extension` = 装进宿主里的扩展
  (ComfyUI 的自定义节点属此);`user_code` = 用户自己的脚本与配置。
- **不叫 `custom_node`** —— 那是 ComfyUI 名词,核心层永不出现特定工具的名词。
- 必填(而非可选)才能让消费侧**删掉**"按 `install_path` 含不含
  `/custom_nodes/` 反推"的路径嗅探。那曾是服务端唯一一处硬编码 ComfyUI
  目录结构的地方,且就在用户可见的配方展示路径上;对微调形态的包(根本
  没有 `custom_nodes/` 目录)它恒判"全是宿主",把用户自己的训练配置也算进去。
- 只有"还没有真实用户"这个窗口买得起必填()。

**`repo_url` / `commit` 为什么改可选** `[实测]`:实测 kohya 用户的
`dataset.toml` 与启动脚本**通常不在任何 git 仓里**。逃生舱**从不 `git clone`**
(它按 `archive.sha256` 拉 tar 解包,`commit` 只用来打一行日志),
故改可选不破既有红线。

"存配方不存成品"():源码归档只存源码,模型走 `files[]` 单独内容
寻址,**绝不混进源码 tar**(否则同字节存两遍;T5 bug7 反向断言)。

### `python_lock`(必填;`lockfile` 子字段 **2.3 起可选**)`[schema]` `[实测]`
uv 生成的确定性依赖锁(uv 是本项目统一使用的 Python 依赖安装/锁定工具)。

| 子字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `tool` | ✔ | const `"uv"` | 锁工具,恒为 uv |
| `lockfile` | | blob | 锁文件本身(见 §7)。**2.3 由必填改可选** |
| `lockfile_path` | | relpath | **2.6 新增**:那份锁文件当年在环境里放在哪 |
| `pinned_wheel_urls` | | **integer ≥0** | **被钉成直连 wheel URL 的包的数量**(计数,非 URL 列表) |
| `wheels_archived` | | boolean(默认 false) | true = wheel 也全量落袋(抗腐烂,体积大) |
| `hosts` | | string 数组 | **2.2 新增**:重建时装依赖会往外连哪些主机(见下) |

**`lockfile` 为什么改可选,以及配套的打包纪律(三档,按顺序)** `[实测]`:
有的环境里就是一个锁文件都没有(ComfyUI 桌面版装出来的环境是实例),
此前 schema 逼着必须有,于是打包端要么崩、要么造一个假的。2.3 起:

| 档 | 情形 | 做法 |
|---|---|---|
| ① | 环境里有锁文件 | 原样落袋 |
| ② | 没锁文件,但**找得到跑这个环境的那个 Python 解释器** | **当场问它要一份现装包清单**(读的是事实不是猜),落袋并在报告里说明来源 |
| ③ | 连解释器都找不到 | **这一栏留空并告警**,不编 |

留空的包**重建不出 Python 环境**,这是它自己的诚实标注,不是漏洞:
`renest lint` 用告警说「信息不全」(`lockfile-missing`),恢复端在第一步就把话讲清楚。

> **两条腿的严格度有意不同**:代理层(`renest restore`)对没有锁文件的包**当场拒绝并说明**;
> 应急脚本对同款输入**降级继续**(跳过装依赖,别的照搬)。这不是漏改 —— 应急脚本的
> 职责是「无论如何把字节弄回来」,代理层的职责是「要么给你一个能跑的环境,要么说清为什么不能」。

**`hosts`(2.2 新增)** —— 重建时装依赖**会往外连哪些主机**,只记主机名不记完整地址。
只记主机名是因为主机名已经足够回答「我的机器会连谁」,而完整地址会把披露面撑爆。
为什么要有:那些地址藏在锁文件**内部**,披露面上看不见,而陌生主机名是最朴素的一个信号。
它与「可信来源白名单强拒」是一对 —— **披露是那道硬拦的事前预告,不是它的替代品**:
只披露不拦是免责声明,只拦不披露是让人在机器前面对一个没预期的失败。

**`lockfile_path`(2.6 新增)** —— 锁文件当年在环境里的位置,相对环境根。
2.6 之前清单里不带它,于是两条恢复路径都按固定约定把锁落在环境根的 `requirements.lock`,
**而且两边都在源码注释里写着"这是约定"**。**微调那两个框架的锁在子目录里**,
照约定落位等于把文件放到框架不会去看的地方。**不填 = 老约定的那个固定落点**,
2.0–2.5 的包全都如此。只有当年那份锁**确实是环境里的一个文件**时才写:
上面第②档是从解释器里问出来的清单,压根没有原始路径,那就不写,
而不是编一个从来不存在的路径出来。

**`pinned_wheel_urls` 是诚实计数字段**:带本地版本号的包(如
`torch==2.4.1+cu124`)只在厂商私有索引、PyPI 上没有,落袋时必须钉成 wheel
直链,否则重建必死在依赖段(T5 第一跑 bug1)。它同时告诉下游:这个锁的
可重建性依赖那台 wheel 主机存活。**注意**:实际的 wheel 直链 + sha256
**住在 `lockfile` blob(uv.lock)内**,顶层只存一个计数 —— restore.sh 无 uv
降级路径的 pip 兼容导出问题由此而来,见 §9-b。

### 4.3 `entrypoint`(可选)`[schema]`

**2.0 新增。** 把"跑通那一次是怎么启动的"从恢复端的硬编码搬进包里。
两种形态都实测过:训练是 `oneshot`( `[实测]` kohya / `[实测]`
LLaMA-Factory,判据 = 退出码 0),ComfyUI 是 `service`(判据 = HTTP 探针)。

| 子字段 | 必填 | 说明 |
|---|---|---|
| `kind` | ✔ | 枚举 `oneshot`(跑完即退) / `service`(长驻) |
| `argv` | ✔ | 字符串**数组**,不是一整条命令行 —— 避免 shell 引用地狱,也让 `redactions` 能按下标定位 |
| `cwd` | | 工作目录,相对环境根;不许绝对路径 / `~` / `..` |
| `env` | | **白名单对象**,见下 |
| `success.exit_code` | | `kind=oneshot` 的成功判据 |
| `success.expect_artifact` | | **2.1 新增**:跑通后应当出现的产物,相对环境根(见下) |
| `ready_probe` | | `kind=service` 的就绪与冒烟判据:`http_get` / `smoke_get` / `timeout_s` |
| `redactions` | | 净化记录数组,见下 |

**`env` 只收白名单键,明令不收 `PATH` 与 `HOME`**:
允许的键是 `VIRTUAL_ENV` / `CUDA_VERSION` / `LD_LIBRARY_PATH` /
`HF_HOME` / `HF_HUB_CACHE` / `FORCE_TORCHRUN`,别的一概被 schema 拒绝。
前三个来自 `[实测]` 的 `run-context.txt` 实测;两个 HF 变量是
本版两个家目录根的对应变量;`FORCE_TORCHRUN` 只有上游文档证据(未实跑),
故允许出现但**不赋予任何必填语义**。`PATH` / `HOME` 是宿主特有的,重建端
自己算 —— 而 **env 是密钥最常见的藏身处**,收整个环境等于把凭证顺手打进包里。

**四个路径型键连『值』也限死**(2026-07-26 定):
`VIRTUAL_ENV` / `LD_LIBRARY_PATH` / `HF_HOME` / `HF_HUB_CACHE` 的值必须是
**重建目录内的相对路径** —— 不许绝对路径、不许 `~`、不许 `..`;
`LD_LIBRARY_PATH` 的**每一个冒号分段**都要满足,**空段**(`a::b`、前后导冒号)
等于"当前目录",同样拒绝。

> **为什么现在就得定死,哪怕今天还没有任何人读这个字段** —— 恰恰因为还没人读。
> 格式允许了这些键、值却是任意字符串;等哪天有人把它接上、真的 export 到环境里,
> `LD_LIBRARY_PATH` 就是**库劫持**的入口(指向包里某个 `.so`,让它抢在系统库
> 前面被加载),而那时格式已冻结、老包已存在,**再想加约束就是破坏性变更**。
> 这正是既有红线的用处:**约束必须赶在字段被消费之前定死**,
> 现在加成本是零。

**给未来消费方的硬要求**:在 export 这些值之前必须按落位闸同样的规则再校验一遍
(`renest.roots.bad_entrypoint_env`),然后把它**拼到重建根之下**,而不是原样
export —— schema 挡的是"包写错了",消费方挡的是"拿到手的别人的包"。

**`success.expect_artifact`(2.1)—— 退出码不够。**
真机撞出过一次假绿:某训练脚本找不到数据时打了一句 `ERROR No data found`,
**却仍以退出码 0 结束**,于是"退出码 0 = 跑通"判绿,而实际一步都没训。
故增这一栏:**声明了它,就必须出现那个产物才算跑通**,即便退出码对。
值是相对环境根的路径(不许绝对路径 / `~` / `..`),判据仍然由包自己声明,
**恢复端不猜框架**。

注意它与"产物不进包"不冲突:这里记的是**产物应当出现在哪**,
产物本身与用户数据一样**永不进包**。

**`redactions`:净化的『记录』在核心层,净化的『知识』在 adapter 层。**
不发明通用净化 DSL —— "哪个参数是产物路径"只有懂那个框架的人知道。
每条:`locator`(✔)、`role`(✔,枚举 `output_dir` / `output_name` /
`log_dir` / `dataset`)、`placeholder`、`note`。

`locator` **两种形式都必须支持**,一种覆盖不了另一种:
`{argv_index: 7}`(kohya 的净化点在命令行下标上, `[实测]`)与
`{file, key}`(kohya 的数据集路径藏在 `dataset.toml` **内部的键**里,
如 `datasets[0].subsets[0].image_dir`)。`role` 的取值全部来自实测:
kohya 的 `--output_dir` / `--output_name` / `--logging_dir` 指向产物、
`--dataset_config` 指向的 TOML 里 `image_dir` 指向用户数据集;
LLaMA-Factory 的 YAML 里 `output_dir` 指向产物、`dataset` 指向用户数据集。

**落袋时序** `[实测]`:装完依赖时 HF 缓存**是空的**,下完基模时只有基模,
**训练之后**才出现 tokenizer。所以在"装完"或"下完模型"这两个时刻落袋,
都会漏掉 tokenizer,重建环境离线跑不起来。这与既有红线
天然一致 —— **必须跑通之后才采,不是保守,是技术必需**。

## 5. 资产:`files`

大文件资产(模型、LoRA、VAE、输入素材等),**一律内容寻址**。数组,每条:

| 子字段 | 必填 | 说明 |
|---|---|---|
| `path` | ✔ | 落位路径,**相对 `root` 指定的根** |
| `root` | | **2.0 新增**,枚举 `env`(默认) / `hf_hub` / `hf_home`(见 §5.1) |
| `blob` | ✔ | 内容寻址 blob(sha256 + size,见 §7) |
| `license` | ✔ | 许可标注(见 §8) |
| `origin_url` | | 原始来源;`serving_scope=gated` 时是下游自取的唯一线索 |
| `sources` | | 有序多源链(见下) |
| `kind` | | **2.7 起是开放字符串**(小写字母、数字、下划线,最长 64 字;**没有取值清单**)。只有 `clip` / `vae` / `tokenizer` / `input_asset` 四个带行为,见下 |
| `serialization` | | **2.2 新增**:这个文件加载时会不会执行代码,枚举 `safetensors` / `pickle` / `other`(见下) |
| `declared_base_model` | | **2.4 新增**:**这个文件自己的头部**声称它是在哪个底模上练出来的(见下) |

**`serialization`(2.2)—— 这个文件加载时会不会执行代码。**
`pickle` 那一类(`.ckpt` / `.pt`)是 Python 的序列化格式,**加载即执行** ——
这是模型投毒最经典的一条路。`safetensors` 只是数据,没这个问题。

**注意它跟 `kind` 分的不是同一件事**:`kind` 分的是**用途**(基础模型/微调件/解码器),
这里分的是**格式**。同一个微调件既可能是 safetensors 也可能是 pickle。
打包时读文件头就知道,零成本;**判不出就不写这个格子**(§1.1 的诚实纪律)。
全绿时它是**正向信号**,该显示出来:「40 个模型全是纯数据格式」。

**`declared_base_model`(2.4)—— 是转述,不是判断。**
训练器保存文件时把这些值写进文件头,打包端把它抄过来,并注明是从哪儿抄的。
子字段:`sha256`(底模的指纹,**照文件头原样抄,小写**)、`family`(文件头怎么称呼这个
底模家族,如 `flux1` / `sd_v1`,**故意留成自由文本** —— 那是训练器的说法,不是我们的说法)、
`stated_by`(枚举 `safetensors_header`,**只要这块里有任何内容它就必填**:
一句没有出处的转述,与我们自己下的结论**分不出来**,而这里只允许前者)。

它凭什么占一个字段 `[实测]`:一个本地练出来的微调件记下了它底模的**全文件 sha256**,
与真正喂给训练器的那个文件的指纹**逐字符相同**;两个不同作者的微调件记着同一个底模指纹,
拿这个指纹去公开索引里问,返回的就是那个底模。也就是说"这个资产要配哪个底模"
**可以用字节回答** —— 不用猜,也不用做任何推荐。

**这里的 `sha256` 是全文件指纹,只是全文件指纹。**
这个生态里有五种指纹都叫 sha256:整份文件的;它的前 10 个字符;从第 1 MiB 处取
64 KiB 窗口再截成 8 个字符的(32 位,真会撞);以及两种跳过文件头、只算张量字节的。
**只有第一种能跟本清单其他地方的地址相比。** 而且**一律小写** —— 有个公开索引回的是
大写,训练器写的是小写,直接做字符串比较就会不相等。
**不填 = 文件头没写、或者没去读,不等于"这个资产没有底模"。**

`kind` 在 2.0 那一版加过三个取值(`tokenizer` = 分词器的 merges/vocab 等文件、
`model_config` = 模型与生成配置、`runtime_config` = 启动器的配置),
当时的纪律是"只加实测见过的,不预留想象中的";2.7 之后**这条纪律不再需要**了 ——
加取值这件事本身取消了,见下。

**`kind`(2.7 起是开放字符串)—— 这个资产是什么种类。**

**只有四个取值对程序有意义:**

- `clip` / `vae` / `tokenizer` —— **共用部件**。一个文本编码器或 VAE 会被塞进几十个
  互不相干的模型里,所以拿它的内容指纹去撞库,撞到的只是*某个装着它的合集*,
  而那个合集的底模跟这个文件没关系。因此许可判定**不许拿共用部件的记录替底模说话**(§8)。
- `input_asset` —— 用户自己的素材:只登记,永不打包。

**其余取值全是给人看的标签**:在列表里显示、在汇总里计数,没有任何代码为它分叉。

**消费方的义务:遇到不认识的取值,就当成一个普通资产。**
永不因此拒包、永不猜它是什么意思、**原样显示**(不许显示成空白,也不许显示成"未知")。
凡是为那四个之外的取值分叉的读取器,都是在把标签当指令读。

**封闭清单为什么取消(2.7)。** 一份枚举去追一个开放生态,永远追不上,
而每漏一个门类就得付一整轮升版的代价 —— 八步清单、两份逐字节相同的逃生舱、
一个人在真机上从头跑一遍。2026-08-12 造"故意很脏的存档"当素材时,
三样真实资产在清单里没有确切位置:装机量前五那个生图扩展的模型、量化权重、视频模型权重;
后两样只能塞进 `checkpoint`,而它们不是那个东西。

**形状规矩不是伪装的清单。** 小写字母、数字、下划线,最长 64 字:
它只保证这一栏是一个机器令牌而不是一句话,于是没人需要去裁定 `IPAdapter` 和 `ipadapter`
是不是同一个东西。**2.7 之前合法的取值全都满足它,所以一个老包都不受影响。**

常见取值(都不特殊):`checkpoint`、`lora`、`controlnet`、`embedding`、`upscaler`、
`tokenizer`、`model_config`、`runtime_config`、`other`,以及 `license_text`(2.2)。
语言模型权重复用 `checkpoint`;许可与说明文件归 `other`。

### 5.1 `files[].root` — 落位根与家目录白名单

原来的 `path` 隐含"资产 = 环境根下的一个文件",ComfyUI 场景恒成立,
微调场景破了:LLaMA-Factory 的基模住在 `~/.cache/huggingface/hub/`
( `[实测]`,9 个文件 954M),kohya 的 CLIP tokenizer 也在那里
( `[实测]`,**且只有真跑过一次才会下载**),accelerate 的配置在
`~/.cache/huggingface/accelerate/`( `[实测]`,训练必需)。

| `root` | 落位根的解析顺序 | 允许的 `path`(schema pattern 强制) |
|---|---|---|
| `env`(默认,不填即是) | 重建目标目录 | 现状不变 |
| `hf_hub` | `$HF_HUB_CACHE` → `$HF_HOME/hub` → `~/.cache/huggingface/hub` | `^models--[^/]+/(refs/[^/]+\|snapshots/[0-9a-f]{40}/.+)$` |
| `hf_home` | `$HF_HOME` → `~/.cache/huggingface` | `^accelerate/[^/]+\.yaml$` |

**为什么白名单写在 schema 的 pattern 里,而不是写成打包侧的排除列表** `[实测]`:训练会把**用户数据集**写进 `~/.cache/huggingface/datasets/`
(`json-train.arrow` 加 tokenize 后的 `cache-*.arrow`),而数据集不进包。两种做错的代价**不对称**:白名单漏一条 → 重建时少个
文件,**用户会发现**;黑名单漏一条 → **把用户数据集传上云,没人会发现**。
写成 pattern 之后,`datasets/…` 在**结构上就写不进 manifest**。

**规则 R1(`renest lint` 强制)**:只要存在任一 `root:"hf_hub"` 且落在
`models--X/snapshots/…` 的条目,就**必须**同时存在同一 `models--X` 的
`refs/<branch>` 条目。依据 `[实测]` 双路径实证:缺了这个 40 字节
的文件,按仓库名取模型会离线失败,而报出来的是 "We couldn't connect to
huggingface.co" —— 一个**彻底误导**的错,用户会以为断网或被墙,无法自查。
故必须在落袋端拦死,不能靠"记得收"。

**落位方式(硬约束,不许改)** `[实测]`:文件以**真实文件**形态
落进 `snapshots/<commit>/`,**带原文件名与扩展名,不建符号链接、不重建
`blobs/`**。理由是实测出来的:kohya 会 `os.path.realpath()` 解引用符号
链接,再用**纯扩展名**判文件类型,而 HF 的 blob **没有扩展名** →
`torch.load()` 去读 safetensors → `_pickle.UnpicklingError: invalid load
key`,**报错完全指不到真因**。"解引用 + 按扩展名判类型"是普遍模式,不止
kohya。故去重只能用硬链接或真实拷贝,**永远不许用符号链接**。

**哈希一律自己算** `[实测]`:HF 的 `blobs/` 是**混合命名空间**
—— 大文件(LFS)名恰好就是 sha256,小文件名是 git sha1(实测反证:
`LICENSE` 的 blob 名 `6634c8cc…18ab` 与实算 sha256 `832dd9e0…e92e` 完全
不同)。"名字碰巧等于 sha256"只能当**校验加速**,不能当唯一来源 ——
吃错了校验会**全绿**(算的和存的是同一个错值),直到重建到别处才炸。

**越界防护与白名单是两件事**:pattern 是白名单,不承担越界防护。
`hf_hub` 那条 pattern 的尾巴 `snapshots/<40hex>/.+` 里的 `.+` **吃得下
`..`**,光靠 pattern 挡不住。对绝对路径 / `~` / `..` 的拒绝在落位闸上
(`restore.sh`、`restore.py`、`renest lint` 三处),**对所有 root 一律生效**。

### `files[].sources`(可选,数组)`[schema]`
有序多源链,按就近/速度排列。代理层赛跑取快、sha256 校验谁赢都一样对。
**逃生舱 `restore.sh` 不读此字段**(只认权威源)。此字段为 v1 **已
预留**;填与不填都不影响 v1 重建。每条:

| 子字段 | 必填 | 说明 |
|---|---|---|
| `url` | ✔ | 源 URL |
| `kind` | ✔ | 枚举:`authoritative`(自持权威源,存在性担保,不可外包)/ `mirror` / `provider_cache` / `torrent` / `magnet`;后四者皆为按哈希校验的可选加速器 |
| `note` | | ≤200 |

> **v1 已冻结的 sources 形状比设计 03 §3.2.3 的 v1.1 提案简单**:v1 只有
> `url/kind/note`,没有 `priority/location/pieces`。后者是 v1.1 提案,
> **不在 v1**。见 §9-d。

## 6. 场景与边界:`adapters` / `api_deps` / `post_install` / `creation`

### 6.1 `adapters`(可选)`[schema]`
场景适配器命名空间;核心字段之外的一切工具专属信息住这里。

**2.0 起是受控开放**:已知 adapter(`comfyui` / `kohya` / `llamafactory`)
各自**严格校验**;未知 key 允许存在,但按**不透明对象**处理(只要求是个
对象,内容不校验)。这样加第四个阵地不必再升一次版,又不让脏数据混进核心字段。

`adapters.comfyui`:
- `workflow`(**必填**,若 comfyui 存在):跑通那次的配方文件(workflow JSON)的 blob。
- `workflow_path`(**2.6 新增**):那个文件当年放在环境里的哪个位置,相对环境根(见下)。
- `workflow_name`:string。
- `verified_run`:"跑通"判定证据 —— `queue_completed_at`(date-time)、
  `duration_seconds`(number)、`output_samples`(blob 数组)。
  **`output_samples` 永不写入**(2026-08-11 裁决),这一栏只为已经带着它的老包保留:
  存一张样张等于替用户保管他自己的画,还要随包递给别人;拿它去比对,
  等于我们去看他画了什么。所以重建之后那道运行检查只回答"这个环境还出得来东西",
  永不回答"出来的是不是同一张画"。**不填是常态,不是信息缺失。**

**`workflow_path`(2.6)—— 三条义务,不是建议。** 打包时读了这个路径、把字节哈希了,
然后**把路径扔了**,于是还原端不知道该把文件放回哪儿,只好丢进一个暂存目录。
"还原 → 改一个地方 → 再打一次"这条最普通的路,第一步就断了:配方不在应用去找它的地方。
读取端必须:

1. 把字节放回这个路径;
2. **那儿已经有个不一样的文件时,保住用户那份** —— 我们这份留在暂存目录,并说明一句,
   **永不覆盖**;
3. 这一栏不填时(2.6 以前的包全都不填)**留在暂存目录并说明,永不自己编一个路径出来**。

放一个文件下去**不等于**启动应用:"逃生舱不负责启动应用"那条裁决管不到这里,
而一个配方拿不回来的存档,不是一个完整的存档。

`adapters.kohya` / `adapters.llamafactory`(2.0 新增,同一形状):
- `config_files`:字符串数组,指向 `files[].path`,标出哪几条是**配方文件**。
  **不新建概念** —— 配方文件就是普通的 `files[]` 条目,内容寻址、校验、
  去重全部白赚,adapter 只负责指名。两个框架的配方载体位置完全不同
  ( `[实测]` kohya 全在 argv 上, `[实测]` LLaMA-Factory 全在一份 YAML 里),
  故 argv 与配置文件两种载体都要能表达。
- `verified_run`:`completed_at` / `duration_seconds` / `exit_code`。的标准跑通判据 = 退出码 0, `[实测]` 与 `[实测]` 双双实证。

### `api_deps`(可选,数组)`[schema]`
外部 API 服务依赖(无法落袋的部分)。**诚实边界字段:逐字节复现承诺不
覆盖此列表** —— 重建后这些节点能否用,取决于服务方存续与用户自备密钥。
每条:`node_name`(✔)、`service`(✔)、`endpoint_hint`(不含密钥)、`note`(≤300)。

### `post_install`(可选,顶层 string)`[schema]`
全局安装后命令(v1 逃生舱:镜像之外的 apt 等系统级操作,人工填写)。

### `creation`(可选)`[schema]` `[实测]`
创建现场元数据:`cloud` / `region` / `upload_bandwidth_mbps` / `agent_version`。

### 6.2 `derived_from`(可选,2.4 新增)—— 预留 `[schema]`

拆包 / 合包做出来的存档,记它是从哪个包派生的。两个子字段,
**只要这块出现就都必填**:`nest_id`(父包的标识,形态与本包的 `id` 相同)与 `version`
(取的是父包的哪一版)—— 一个没有版本的父包,落不到具体字节上。

**预留字段:本版打包端一行都不会写它** —— 会写它的那个功能还没做。
现在放进来,是为了让第一版实现不必再升一次格式版本号。

两条读法比形状要紧:
**不填 = "不是从任何包派生的",永远不等于"不知道"** —— 反过来读,
每一个普通存档看上去都像丢了自己的来历;
**它是一张死快照**,指名父包的某一个版本,**不跟着父包后来的版本走**。
任何把它解析成"父包现在是什么样"的实现,做的都是另一个产品,而且是个会吓人的产品:
存档的意义就在于它不会自己变。

### 5.2 落位形态:永远是真实文件或硬链接,**永不用符号链接做去重** `[2.3 写死]` `[实测]`

**这条是硬约束,不许"优化"。** 去重可以用**硬链接**(同一份字节、多个真实名字)
或直接拷贝,**但永远不许用符号链接**(一个指向别处的指针)。

**依据是真机血案**:某训练框架会先把符号链接解引用到它指向的真实文件,
再**按扩展名**判断这是什么类型的文件 —— 而被指向的那份内容寻址副本**没有扩展名**,
于是它拿一个纯数据格式的模型走了"执行代码"那条读取路径,报出来的是
`invalid load key` 之类的错,**完全指不到真因**。
「解引用 + 按扩展名判类型」是普遍模式,不止这一个框架。

**推论(打包侧)**:如果被打包的**代码目录本身**是一条符号链接,
tar 存下来的是那条链而不是树里的文件 —— 5 KB 的插件打出 400 多字节、
**逐字节校验全绿**、解包却什么都不落。恢复端必须拦住这种包(见下)。

**错误码 24(`SYMLINK_BROKEN`)的产生条件,写清** `[实测]`:
归档**逐字节校验通过、解包出来却是 0 个成员**时,恢复端必须以码 24 失败,
并说清「问题不在你这台机器上、重跑没用、要打包的人把那条链换成真实目录再打一次」。
落点:`renest.restore` 解包那一步(`_extract_strip1` 返回 0 时抛 `SYMLINK_BROKEN`)。
> 这一条 2.3 之前**只登记在规范里、全仓没有任何代码产生它** —— 一个只写在纸上的错误码
> 比没有更坏:它让人以为这种情况被处理了。现在有代码了,条件也写死在这里。

### 5.3 同一份内容被多个路径引用:合法形态,取一次落多处 `[实测]`

同一个 sha256 出现在多条 `files[]` 里(不同 `path`)是**合法形态**,不是错误 ——
内容寻址天然如此:两个不同名字的文件内容完全相同,就是同一个内容块。

**恢复端**应当**按内容去重取字节:取一次,落多处。**

> **这是"应当",不是"必须",而且现状还没做到** —— 说清楚免得读的人以为已经这样了。
> 现状是两条腿都会**重复下载**:一个大模型被引用 N 处就下 N 遍。
> 一份 20 GB 的模型被引用两次,就是白等一倍的时间、白付一倍的流量。
> **本版先把"应当"写进规范,实现随后**(不在 2.3 范围内)。

**去重时的落位方式受 §5.2 约束**:第二处及之后用硬链接或真实拷贝,**不许用符号链接**。

### 5.4 保留路径:`.renest/escape/restore.sh` —— 应急脚本跟着包走 `[实测]`

`.renest/escape/restore.sh` 是**约定路径**,打包端把那份"不依赖我们任何代码也能把包
解开"的应急脚本当成一个**普通 `files[]` 条目**放在这里(`root:"env"`、`kind:"other"`,
内容指纹与体积走现有机制自然记下)。**本版不为它新增任何顶层字段** ——
版本信息放在**脚本自己的头部注释里**。

**为什么要有这条约定**(2026-08-02 有人问:"用户很早前打的包放在自己的存储里,
两年后他怎么把东西弄回来?"):应急脚本存在的**全部理由**是「哪怕我们这家公司没了,
你的东西也拿得回来」。可它此前**不在包里** —— 用户得回我们的仓库翻当年那一版,
**那等于要求我们还活着**,把这个脚本自己的承诺打了脸。

**代价约等于零**:脚本几十 KB,按内容寻址存,同一个版本**全网只存一份**
(一万个用同一版本的用户共用那一份;再出一版才多一份)。

**代价在另一头,必须主动说**:包里那份是**冻住的**,以后修的毛病到不了老包。
诚实说法是两层 ——
> **包里那份 = 保底**:任何时候、哪怕我们没了,它都能把你的东西弄回来。
> **我们这儿的最新版 = 更好**:修过毛病,而且能读好几代老格式。
> **够得着我们的时候,用新的。**

**安全话(不说就等于开了一条投毒通道)**:
> **你自己打的包**:里面的脚本就是当年那一版,直接用。
> **别人递给你的包**:用你自己那份;真要用包里那份,**先核对内容指纹** ——
> 指纹本来就记在这条 `files[]` 里,核对是白赚的。

## 7. `$defs.blob` — 内容寻址文件指针

所有大文件、归档、锁文件、workflow、样张统一用 blob 指针:

| 子字段 | 必填 | 说明 |
|---|---|---|
| `sha256` | ✔ | `^[a-f0-9]{64}$` 小写十六进制 |
| `size_bytes` | ✔ | integer ≥0 |

物理位置 = `<bucket>/blobs/sha256/<hash 前2位>/<完整 hash>`。sha256 是一等
公民(既有红线,与 Civitai/HuggingFace/CivArchive 生态互认,不换 BLAKE3)。
内容寻址 + 硬链接布局:打包侧"先铺 blob 树再上传",overlay 上硬链接生效
不翻倍(T5 三节 bug2)。恢复端全量逐字节校验(T5 26/26 一致,P1 附录 A)。

### 7.1 发布顺序是规范的一部分 `[实测]`

**`manifest.json` 出现在桶里 = 这个包完整可取。** 这是一条**规范级承诺**,不是某个
实现的内部细节 —— 恢复端(代理层与逃生舱都)以 manifest 为起点,它读到清单就认为
里面列的每个 blob 都能取到。

故任何往桶里发布的实现(`renest pack --dest s3`、`--dest hosted`、手工 `s5cmd`/`rclone`
同步)**必须**遵守:

1. **先 `blobs/`,后 `nests/`**。所有 blob 就位之后才写 `nests/<id>/manifest.json`;
2. **任一 blob 失败 → 一个 manifest 都不写**。桶里最坏的状态是"有字节没清单"——
   那是**不可读**的中间态,重建方不会开始,所以不会看到半个包;
   反过来先写 manifest 会造出"有清单没字节"的**可读半包**,重建方逐个 404;
3. **断了就重跑**。blob 是内容寻址的,重跑天然幂等:桶里已有同名同大小的对象直接跳过,
   只补没传完的,最后再写 manifest。**不需要手工清理**;
4. **分段上传失败要中止**(`DELETE ?uploadId=…`)。已传分段不会出现在对象列表里,
   但会持续计费到桶的生命周期规则清掉它 —— 不中止等于给用户留一笔看不见的账。

手工同步的用户请按同一顺序做:`blobs/` 传完确认无误,再传 `nests/`。

## 8. `$defs.license` — 许可标注

驱动分享/转存规则引擎。**两个正交开关**:

| 子字段 | 必填 | 说明 |
|---|---|---|
| `shareable` | ✔ | boolean。管**授递面**:false = 分享时自动摘除,接收方获自助补齐指引 |
| `serving_scope` | ✔ | 枚举 `private` / `open` / `gated`。管**供给面**:能否跨用户从去重池供出 |
| `spdx` | | 如 `Apache-2.0`;自定义许可留空 |
| `tag` | | 内部四档:`permissive` / `capped` / `rail` / `restricted` / `unknown` |
| `note` | | ≤500 |
| `declared_by` | | **2.2 新增**:这条许可是**查出来的**还是**用户自己填的**,枚举 `detected` / `user` |
| `gated_form` | | **2.2 新增**:受限的两种形态,枚举 `none` / `auto` / `manual` |
| `attribution` | | **2.2 新增**:署名要件,`author`(≤200) + `url` |
| `text` | | **2.2 新增**:这条资产的**许可原文**在哪(blob,见 §7) |

**`declared_by`(2.2)—— 这句话是谁说的。**
2.2 之前,包里每一条许可都是打包人写进输入清单、**未经任何核实**的声明,
被原样抄进 manifest 当成判定结果。没有这个格子,判定做完了也**分不清哪些是查的、哪些是抄的**。
缺席 = 不确定(老包如此)。出纠纷时它回答的就是「这句话是谁说的」。
`renest lint` 配一条闸:说了 `detected` 却既说不出许可名、也说不出来源 → 告警(那是空话)。

**`gated_form`(2.2)—— 受限的两种形态,别合成一个词。**
`auto` = 点一下同意就能下,几秒钟;`manual` = 要向作者申请,**可能等几天**。
对收件人是**完全不同的等待预期**。实测坐实(2026-07-29):同一批模型里三种形态都有。
`renest lint` 配一条闸:标了受限形态、`serving_scope` 却不是 `gated` → 报错(两者自相矛盾)。

**`attribution`(2.2)—— 没有它,"只要署名就随便用"那一档许可永远开不了。**
有一类许可允许任何目的(含商业)自由分发,**唯一条件就是署名**。
记下来还不够 —— 收件人那一侧要真的把它显示出来。

**`text`(2.2)—— 许可原文跟着字节走。**
有一族许可要求**分发时把使用限制一并交付**,最直接、最不容易出错的做法就是让原文
跟着字节走,而不只是在用户协议里写一句。

**做法:不去源头捡,带标准原文。** 实测三种情况,第三种让"从仓库抓"这条路走不通 ——
仓库有且本地也下了(能抓)/ 仓库有但下载模型时不会捎上 / **仓库压根没有**
(实测某个常用视觉模型的 13 个文件里一个许可文件都没有)。
名单上的许可总共就那么几个、每个只有一份标准原文,随工具带着即可。

它指向的就是 `files[]` 里一条 `kind=license_text` 的**普通文件** ——
内容寻址、去重、校验全白赚,同一份许可原文全网只存一份。
`renest lint` 配一条闸:`text` 指向的字节**不在这个包里** → 报错(等于没带,而要求就是"带着")。

`serving_scope` 三级(,捕获时刻写死、封袋定死、restore 端照单执行
无临场裁量):
- `private` = 分享者自有资产(自训 LoRA / workflow / 自有素材),直供已授权收件人;
- `open` = 许可允许再分发(Apache-2.0 / MIT / 可再分发 OpenRAIL),跨用户池开放当加速层;
- `gated` = 受限许可(FLUX-dev、禁转载 Civitai 资产等),副本只服务本人重建,
  永不跨用户供字节,下游只拿 `origin_url` + sha256 自持凭证取。

**默认拒绝**:查不到许可一律默认 `gated`。**约束**:`gated ⇒ shareable 必须
为 false`(schema 未用条件约束强制此蕴含,见 §9-f)。

### 3.1 `gpu.package_native_archs`(可选,2.0 新增) `[实测]`

Python 依赖里**预编译扩展各自**的目标架构档。与既有 `gpu.node_native_archs`
同一思路、同一诚实纪律(`cuobjdump --list-elf` 探不到就不记),对象换成 pip
装进来的包。每条:`package`(✔)、`path`(✔,相对 site-packages)、`sm_list`(✔)。

**字段形状是量完才定的,不是照描述凭空写的。** 2026-07-26 在 RTX 3060 上实测
torch 2.6.0+cu124 / xformers 0.0.29.post3 / bitsandbytes 0.50.0(29 个 `.so` 的原始 `cuobjdump` 输出全在)。
测量结果直接改了三处设计:

| 量到了什么 | 对字段的影响 |
|---|---|
| 同一个包内不同 `.so` 的档就不一样(bitsandbytes 的 7 个可探 `.so` 有 **3 种**不同档组合) | **必须逐 `.so` 记,不能按包聚合** |
| 29 个 `.so` 里 **18 个探不到**(62.1%):纯 CPU 库、ROCm/XPU 变体、C++ 胶水层 | **"探不到就诚实略过"是必须的分支,不是可选的** |
| `xformers/_C.so` 的档是 sm_60/70/75/80/90,**没有 sm_86**,而打包机自己就是 sm_86 的 RTX 3060;反过来 bitsandbytes 的 cuda128/130/132 带 sm_100/sm_120,**宽于** torch 的 arch_list | **只看 `torch_cuda_arch_list` 会错,而且两个方向都会错** —— 预检要取交集,不是取 torch |

**消费侧还有一条注意**:一个包可能**按 CUDA 版本各带一份 `.so`**
(bitsandbytes 从 `cuda118` 到 `cuda132` 共七份),运行时才选一个。
所以不能把一个包里所有条目无脑取交集 —— 该取的是**会被真正加载的那些**。
本字段只负责如实记下形状;消费实现归跨代迁移引擎那批(跨代迁移那批),不在本版。

### 与 2.0 相关但**不是**格式变更的两条判据 `[实测]` 暴露的 CUDA 问题要的是**判据不是格式**,故进
`data/doctor-rules.json`(走既有热更新通道):

## 12. 2.6 改了什么(2026-08-12)

**纯增量,四个字段全可选,2.0–2.5 的包全部照读。** 没有收紧任何东西,也没删任何东西。

这四个的共同点是:**打包时本来就知道,然后随手扔了。**
起因是有人手工搬了一个存档,发现配方并不在打包输入清单说的那个位置;
接着按字段逐个清了一遍整份格式 —— 对着写它的那段代码,和读它的那四处。

| # | 字段 | 破坏兼容吗 | 为什么 |
|---|---|---|---|
| ① | `adapters.comfyui.workflow_path`(§6.1) | 否(增量) | 打包把配方哈希了、把路径扔了,于是还原只能丢进暂存目录。"还原→改一处→再打一次"第一步就断 |
| ② | `python_lock.lockfile_path`(§4) | 否(增量) | 两条恢复路径都按固定约定把锁落在环境根**并且都在源码注释里写着这是约定**;而微调那两个框架的锁在子目录里 |
| ③ | `code_deps[].exclude`(§4) | 否(增量) | 没有它,收件人分不出完整源码与被裁过的源码 —— 同仓库、同提交号、少一个目录,清单看上去很健康 |
| ④ | `runtime.native_libs`(§3) | 否(增量) | 操作系统的库打不进存档。缺一个的机器逐字节还原全对、应用也起得来、也应答,却静默丢掉整个插件 `[实测]` |

**为什么四个一起做。** 升一次版真正贵的不是字段,是那八步清单、
两份逃生舱脚本逐字节保持一致、以及事后一个人在真机上从头跑一遍。分开做就要付两遍。

### 2.6 顺手改正的措辞(不动形状)

`adapters.comfyui.verified_run.output_samples` 在本文件里一直写着"重建后像素级比对的基准"。
那句话在 2026-08-11 就不成立了(当天裁定永不存样张),schema 当时改了、散文没改。
现在两边一致(§6.1)。

### 明确不做什么(2.6)

| 不做 | 依据 |
|---|---|
| 不给微调那两个适配器加 `workflow_path` | 它们没有这个毛病:配方文件本来就是普通的 `files[]` 条目,自带真实路径 |
| 清点查出一批"没人写也没人读"的字段,但一个都不删 | "没人读"和"该删"是两回事。预留字段本来就该没有读者,其中两个的说明里自己写着这一点 |
| 不给操作系统库名附带版本号 | 名字按索要时的原样记,而多数名字与磁盘上的文件差的恰好就是版本 `[实测]`;补版本等于我们去编一个 |
| `declared` 那份库清单永不用来拒绝重建 | 它只覆盖真实加载量的一部分,还列着从没被加载的库;有台机器缺四个照样正常出图 `[实测]` |

## 13. 2.7 改了什么(2026-08-12)

**只改一处,而且只放宽**:`files[].kind` 由十三个门类的封闭枚举改成带形状约束的开放字符串。
2.7 之前合法的取值现在全都合法,所以 2.0–2.6 的包一个字不用改,也没有任何存档需要重打。

| # | 变更 | 破坏兼容吗 | 为什么 |
|---|---|---|---|
| ① | `files[].kind`:去掉 `enum`,改成 `pattern` + 长度上限(§5) | 否(纯放宽,老取值全部仍然合法) | 一份枚举追不上一个开放生态,而每漏一个门类就要付一整轮升版 |

**是什么逼出来的。** 2026-08-12 造一个"故意很脏的存档"当素材时,
三样真实资产在清单里没有确切位置:装机量前五那个生图扩展的模型、量化权重、视频模型权重。
后两样只能塞进 `checkpoint` —— 而那不是它们;**一个错的门类比一个陌生的门类更坏。**

**这一栏到底管什么。** 只有一条规则真的看它:`clip` / `vae` / `tokenizer` 标记
**共用部件**,它们的许可不许替底模说话;`input_asset` 标记用户自己的素材。
它的机器含义到此为止,其余全是给人看的标签。**为了标四个取值而去枚举全世界,从来就不成立。**

**放宽掉的唯一一道真闸,以及拿什么补上。** 老枚举能拒掉一件事:
把搜索目录名 `text_encoder` 写进这一栏(法定名是 `clip`)—— 那个错误恰好会让
共用部件那条许可规则失效,当年花了一次云上跑批才炸出来。开放字符串拒不掉它,
所以检查器改成**说**出来:告警 `kind-is-a-folder-name`,只对"这个资产确实是共用部件"
的目录名发出,并在 `renest pack` 里**赶在机器开始计费之前**打出来。
**只告警,永不拒绝** —— 拒绝陌生门类正是这一版要取消的行为。

### 明确不做什么(2.7)

| 不做 | 依据 |
|---|---|
| 不为那三样资产各加一个枚举值 | 一个一个加取值,正是这一版要终结的做法 |
| 不动 `code_deps[].role`(`host` / `extension` / `user_code`) | 那份清单是真封闭、也真够用:它命名的是我们自己的三个位置,不是全世界的资产门类 |
| 不动许可规则本身 | 共用部件那条规则原样不动;这一版要做的只是确保放开 `kind` 没有把它削弱 |
| 不做大小写折叠、不做同义词表、不做规范化 | 裁定 `ipadapter` 与 `IPAdapter` 是不是同一个东西,就是我们在裁定事物是什么。形状规矩让这个问题不出现 |

## 16. 2.8 改了什么(2026-08-17)

**一个可选字段,纯增量**:`runtime.contested_modules`(§3)。2.0–2.7 的包全部照读;
没有这个字段的存档在两条还原路径上行为与从前完全一样。

| # | 变更 | 破坏兼容吗 | 为什么 |
|---|---|---|---|
| ① | `runtime.contested_modules[]` —— 锁里几个包都往同一个目录写文件时,跑通那一次用的那份属于哪个包,以装完的文件指纹为凭 | 否(增量、可选) | 同一份锁、同一台机器、背靠背装三次 → 三次里有一次赢家不同,`pip list` 逐次相同。只有打包机知道跑通的是哪份,也只有装完的字节能认出它 `[实测]` |

**是什么逼出来的 `[实测]`。** 一套真人天天在用的环境里,`opencv-python-headless` 与
`opencv-python` 并存;带界面那个赢,只因为它晚装了四个小时;七个插件经它 import `cv2`,
换到一台没有 `libGL.so.1` 的云机器上,七个一起挂,报错只说找不到那个库、不说根因。
这套环境活着靠的是安装顺序的运气 —— 而锁钉不住运气。

**两步,以及为什么第一步不够。** 第一步(同一版工具里的改动,不动格式):装完之后点名
赢家缺哪些机器库 —— 把静默失败变成一句告警。第二步(本版):让赢家就是跑通那次的那份。
光告警做不到这一点:打包机自己再装一次也可能换赢家,没有稳定的"原样"可核,除非存档钉住它。

### 明确不做什么(2.8)

| 不做 | 依据 |
|---|---|
| 不记通用的"安装顺序" | 顺序既不是锁能承诺的,也不是决定结果的东西;决定结果的是活下来的字节。记那个文件更小、更准 |
| 指纹不同不拒绝 | 这是 declared 级陈述(读的是装完的文件,不是跑通那次的现场),declared 级只许告警 —— 与 `native_libs` 同一条线 |
| 哪些包会打架不进格式 | 这是会变的外部事实,格式不该跟着它升版;今天随工具的规则走(先只有 `cv2`),将来挪进签名下发的判据包也不必升格式 |
| 不逐文件记,一个模块记一个文件 | 决定行为的是那个编译模块,目录里其余文件跟着它走 |
